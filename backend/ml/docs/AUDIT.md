# Phase 1–2: Repository Audit & Dataset Discovery

Date: 2026-08-12 · No code was modified during this audit.

## Existing architecture

Clean Architecture, dependency-injected end to end:

```
Controller  app/api/v1/forecast.py     thin routes
Service     app/services/forecast_service.py   business logic (MOCK engine)
Repository  app/repositories/{forecast,sales,product,warehouse}_repository.py
Model       app/models/{forecast_history,sales_history,product,warehouse}.py
```

DI wiring: `app/core/dependencies.py` → `get_forecast_service(db)` builds
`ForecastService(ForecastRepository, ProductRepository, WarehouseRepository)`.

## Existing forecast schema (must not change)

Request: `product_id: UUID`, `warehouse_id: UUID`, `start_date`, `end_date`
(≤ 365 days), `model: "prophet"|"xgboost"|"lstm"`.

Response: `forecast_id`, `product_id`, `warehouse_id`, `model_used`,
`prediction_date`, `confidence_level`, `points: [{date, predicted_demand,
lower_bound, upper_bound}]`, `metrics: dict`.

Frontend types (`frontend/src/types/index.ts`) mirror this exactly.
**Contract constraint found:** `frontend/src/pages/forecast.tsx:278-284` calls
`m.metrics.mape.toFixed(1)` (and `rmse`, `mae`) **unguarded** on
`GET /forecast/models` — those three keys must always be numbers. History-run
metrics are guarded with `typeof` checks.

## Existing mock ML service

`ForecastService._generate_points` — a seeded `random.Random` producing
deterministic base + trend + weekly/annual seasonality + noise. **Metrics are
fabricated** (`rng.uniform`). The docstring explicitly designates
`_generate_points` (or an injected model adapter) as the replacement point.
`ForecastService.models()` hardcodes three models with `status="planned"` and
placeholder metrics.

## Database fields related to sales

`sales_history`: `product_id → products`, `retail_store_id → retail_stores`,
`date`, `quantity_sold: int`, `revenue: float`. Composite index on
`(product_id, date)`.

Hierarchy: `Factory → Warehouse → RetailStore → SalesHistory`. Sales attach to
**retail stores**, not warehouses; `retail_stores.warehouse_id` (nullable)
gives the warehouse linkage, so warehouse-level demand = sales aggregated over
the stores a warehouse serves.

## Dataset discovery

- **No CSV/Excel/JSON/parquet dataset files exist** anywhere in the repo.
- The only historical data is the **seeded database** (`backend/dev.db`,
  generated by `scripts/seed.py`):
  - 18,250 sales rows · 50 products · 15 retail stores · 10 warehouses
  - Date range 2025-08-06 → 2026-08-05 (365 days, exactly 1 year)
- The seed generator is **synthetic**: per-product `base + trend`, weekly
  seasonality (`WEEKDAY_FACTORS`), annual sinusoid, Gaussian noise; zero-sale
  days are dropped (not stored).
- **Critical property:** each sale row is assigned to a *uniformly random*
  retail store (`rng.choice(stores)`). The store→warehouse dimension therefore
  carries **no signal** — a (product, warehouse) slice is a random ~1/10
  subsample (~36 scattered days/year). The meaningful forecasting unit is the
  **product-level daily series** (sum over stores), which is dense and has
  real structure (trend + two seasonalities).

**Dataset selection decision:** use the seeded DB aggregated to daily
product-level demand (`SUM(quantity_sold) GROUP BY product_id, date`) as the
development dataset, clearly labelled synthetic. Per §8 of the spec, when a
requested (product, warehouse) series lacks sufficient history the pipeline
falls back to product-level forecasting and says so (`series_level` metadata)
rather than fabricating warehouse signal. The loader also accepts CSV files so
a real dataset can replace the DB source without code changes.

Answers to §30 (dataset requirements):

| Question | Answer |
|---|---|
| Target variable | `quantity_sold` (aggregated daily → `demand`) |
| Time column | `date` (daily) |
| Product identifier | `products.id` (UUID; `sku` human-readable) |
| Location identifier | `retail_stores.warehouse_id` (nullable, random ⇒ weak) |
| History available | 365 days per product (1 seasonal cycle) |
| Missing dates | yes — zero-demand days were dropped by the seeder; must be reindexed to 0 |
| Zero-demand periods | yes, after reindexing ⇒ MAPE unsafe, use safe-MAPE/sMAPE/WAPE |

Modelling consequences: **yearly seasonality must stay off** (only one cycle
observed — it cannot be separated from trend); weekly seasonality on; lag
features up to 28 days are supported.

## Potential integration points

1. `ForecastService.predict` — inject an ML adapter before the mock path;
   mock remains the fallback when no trained model exists (contract identical).
2. `ForecastService.models()` — read real status/metrics from the model
   registry; `status` flips `"planned"` → `"available"` (field documented for
   exactly this).
3. `ForecastPredictResponse.metrics` / `ForecastHistory.metrics` (JSON dict) —
   carry real evaluation metrics + provenance (engine, model version,
   series level).
4. Future consumers: `SimulationService`, `DigitalTwinService`,
   `RecommendationService` can call the ML `predict_demand` interface.
